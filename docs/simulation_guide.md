## 第1部 シミュレーションの基本

### 1.1 シミュレーションとは何をしているのか
ロボットのシミュレーションは、次の繰り返しである。

```
  ┌─────────────────────────────────────────────┐
  │ 1. 今の状態を読む   (関節の角度、物体の位置)   │
  │ 2. 指令を決める     (各モータの目標位置)       │
  │ 3. 指令を与えて、わずかな時間だけ物理を進める  │
  └──────────────┬──────────────────────────────┘
                 └─ これを何千回も繰り返す
```

3 の「わずかな時間」を **タイムステップ (timestep)** と呼ぶ。このプロジェクトでは 0.002 秒。
1 秒のシミュレーションには 500 回のステップが必要になる。

重要なのは **「シミュレーション内の時間」と「現実の時間」は別物** という点。
計算が速ければ 1 秒のシミュレーションが 0.1 秒で終わるし、重ければ 10 秒かかる。
(ビューアで現実と同じ速さで再生するには、わざと待つ処理が要る。`view_grasp.py` がそれ。)　
```
シミュレーションは、現実よりはるかに速く終わります。さきほど測ると、シミュレーション時間4秒分の計算が、実時間0.02秒で終わりました(約177倍速)。

そのままビューアで表示すると、4秒の動きが0.02秒で終わり、一瞬で最後の姿勢になって見えません。そこで view_grasp.py では、シミュレーションを現実の時計に合わせて進めています。

while env.data.time < time.time() - t0:   # シミュレーション時間が、実際に経った時間より遅れている間だけ
    env.step(...)                          # 追いつくまで進める
time.sleep(0.005)                          # 追いついたら少し休む(待つ処理)

- env.data.time はシミュレーションの時計です。
- time.time() - t0 は、再生を始めてから実際に経った秒数です。
- 実際の時間が1秒進めば、シミュレーション時間も1秒分だけ進める、という仕組みです。
- 動画を作る demo_grasp.py は待たずに一気に計算します(速いほうが得だからです)。
```

### 1.2 MuJoCo の 2 つの主役: `model` と `data`
MuJoCo はこの 2 つの入れ物で世界を表す。**この区別が最も大事。**

| | `model` (`MjModel`) | `data` (`MjData`) |
|---|---|---|
| 中身 | **変わらない設定** | **刻々と変わる状態** |
| 例 | 物体の形、質量、関節の種類と範囲、摩擦、タイムステップ | 今の関節角度、速度、時刻、接触、モータへの指令 |
| 作り方 | XML ファイルから読み込む | `model` から作る |
| 書き換え | 基本しない | 毎ステップ変わる |

たとえるなら、`model` は「ゲームのステージ設計図」、`data` は「いまのゲーム進行状況(セーブデータ)」。
同じ `model` から複数の `data` を作れば、同じ世界を並行して何個も動かせる (後の強化学習などで役立つ)。

### 1.3 モデルを記述する XML (MJCF)
`models/scene.xml` の中身は、おおまかに次の入れ子構造になっている。

```
<mujoco>
  <option>      物理計算の設定 (タイムステップなど)
  <asset>       色・テクスチャなどの素材
  <default>     共通の初期値
  <worldbody>   ★世界に存在するものの「木構造」
     ├ 床、カメラ、ライト
     ├ <body palm>            手のひら
     │    ├ <joint palm_z>    ← 上下にスライドする関節
     │    ├ <geom>            ← 形(箱)
     │    ├ <body finger_l>   左の指 (手のひらの「子」)
     │    │    └ <body>       指先側 (指の「子」)
     │    └ <body finger_r>   右の指
     └ <body target>          つかむ物体
  <actuator>    ★モータ (関節を動かす力の出どころ)
```

主要な 4 つの部品:

| 部品 | 意味 | このプロジェクトでの例 |
|---|---|---|
| **body** | 動く「かたまり」(剛体)。親子関係を持つ | 手のひら、指の各節、物体 |
| **joint** | body を親にどう繋ぐか(動ける向き) | `slide`=直線、`hinge`=回転、`free`=完全に自由 |
| **geom** | 見た目と**衝突判定**の形 | 箱、カプセル(丸い棒) |
| **actuator** | 関節を動かすモータ | `position`=目標位置を指令する方式 |

**親子関係が大事**: 指(子)の位置は手のひら(親)に対する相対位置で書く。
だから手のひらが下がると指も一緒に下がる。関節を持たない body は親に固定される。

**単位**: 長さ=メートル、角度=ラジアン(180° = 約3.14)、質量=キログラム、時間=秒。
XML 冒頭で `angle="radian"` と指定しているのは、角度をラジアンで書くという宣言。

### 1.4 状態を表す配列: `qpos`, `qvel`, `ctrl`
`data` の中の主な配列。**「何番目が何か」は XML に書いた順で決まる。**

| 名前 | 意味 | このプロジェクトでの中身 |
|---|---|---|
| `qpos` | 全関節の位置 | `[palm_z, l_prox, l_dist, r_prox, r_dist, 物体の位置x,y,z, 物体の姿勢(4要素)]` |
| `qvel` | 全関節の速度 | qpos に対応 (ただし物体の姿勢は3要素なので全体で11個) |
| `ctrl` | モータへの指令値 | `[手のひら, 左基節, 左先節, 右基節, 右先節]` の5個 |

実際にこのモデルで調べると `qpos` は 12 要素、`qvel` は 11 要素、`ctrl` は 5 要素だった。
`qpos` が `qvel` より 1 つ多いのは、`free` ジョイントの姿勢を「四元数(4要素)」で表すため
(回転の速度は3要素で足りる)。この違いは最初に混乱しやすい。

#### `qpos` / `qvel` / `ctrl` という名前について
- **XML には `qpos` という文字は一切出てこない。** これは XML の部品ではなく、MuJoCo が XML を読み込んだあとに
  **自動で作る配列の名前**で、`data.qpos` のように Python から読み書きする。
  中身は、XML に書いた `<joint>` の位置 (角度や距離) を、決まった順に1列に並べたもの。
- **`qpos` = 「q」+ position (位置)**。「q」はロボット工学・力学で **一般化座標** (その系の姿勢を決める変数の組) に使う記号。
  「joint (関節) の位置」と読み替えてよい。同様に `qvel` = q の velocity (速度)。
  `ctrl` は control (制御) の略で、こちらは `q` と無関係 (モータへの指令値)。
- 「関節 1 個につき 1 要素」が基本 (`slide` と `hinge` は 1 個ずつ)。ただし `free` ジョイントだけ特別で、後述のとおり複数要素を使う。

#### なぜ `qpos` が 12 個で `qvel` が 11 個なのか (四元数の話)
関節ごとの要素数を数えると分かる。

| 関節 | 種類 | qpos の数 | qvel の数 |
|---|---|---|---|
| `palm_z` | slide | 1 (高さ) | 1 |
| `l_prox`, `l_dist`, `r_prox`, `r_dist` | hinge | 各 1 (角度) → 4 | 各 1 → 4 |
| `target_free` | free | **7** (位置 x,y,z の3 + 姿勢の4) | **6** (並進速度3 + 回転速度3) |
| **合計** | | **5 + 7 = 12** | **5 + 6 = 11** |

- 空中に浮く物体 (`free`) は、位置 (x, y, z) と「どちらを向いているか (姿勢)」の両方が必要。
- **姿勢を表す方法の1つが四元数 (クォータニオン)**。`(w, x, y, z)` の 4 つの数で向きを表す。
  4 個使うが、「長さを 1 にそろえる」という制約があるので、実質の自由度は 3 (前後・左右・ひねりの 3 方向)。
  (なぜ 3 個ではなく 4 個かというと、3 個の角度 (オイラー角) で姿勢を表すと、特定の向きで計算が壊れる「ジンバルロック」が起きるため。
  四元数はそれを避けられる。物理エンジンやゲームで定番の表現。)
- 一方、**回転の速さ**は「x 軸まわりに毎秒何 rad、y 軸まわり…、z 軸まわり…」の **3 個で十分**。制約もない。
- したがって `free` ジョイントは、位置の側 (qpos) が 7 個、速度の側 (qvel) が 6 個になり、全体で 1 個ずれる。
- 実用上の注意: **qpos と qvel の添字は 1 対 1 に対応しない**。`qvel[i]` が `qpos[i]` の速度、と考えてよいのは `free` ジョイントより前 (= ハンドの 5 関節) だけ。

> **注意**: `qpos` の先頭5個がハンドの関節なのは、**`models/scene.xml` の `<worldbody>` の中で、ハンド (`<body name="palm">`) を物体 (`<body name="target">`) より先に書いたから**。
> MuJoCo は `<worldbody>` を **上から順に (親→子の順にたどって)** 見て、見つけた `<joint>` に 0, 1, 2, … と番号を振る。
> 実際の並びは次のとおり (実行して確認した)。
>
> ```
> 番号  joint 名      (scene.xml での位置)
>  0    palm_z        palm の中
>  1    l_prox        palm の中の finger_l
>  2    l_dist        その子
>  3    r_prox        palm の中の finger_r
>  4    r_dist        その子
>  5〜11 target_free  最後に書いた物体 (free ジョイントなので 7 要素)
> ```
>
> もし `scene.xml` で `target` の `<body>` を `palm` より**前**に移動すると、`qpos[0:7]` が物体の値になり、
> `env.py` の `joint_pos()` (= `qpos[:5]` を返す) は**ハンドの関節ではなく物体の位置と姿勢を返す**ようになる。エラーは出ず、値だけが静かに間違う。
> (`ctrl` の並びは、同様に `<actuator>` に書いた順で決まる。)

### 1.5 位置アクチュエータの仕組み (PD 制御)
`<position>` のモータは、目標位置 `ctrl` に向かって関節を引っ張るバネのように働く。

```
 力 = kp × (目標位置 − 現在位置) − kv × 速度
        └ バネ(P項)                └ ダンパ(D項)
```

- **kp (位置ゲイン)**: 大きいほど目標へ強く引く。大きすぎると振動したり不安定になる。
- **kv (速度ゲイン)**: ブレーキ。行き過ぎ(オーバーシュート)を抑える。
- これは現実のサーボモータ(目標角度を指令して使うタイプ)とよく似た考え方で、後で実機に移すときにも通じる。

重要な帰結: **`ctrl` に入れるのは「力」ではなく「目標位置」**。目標に届かなくても(物体に当たって止まっても)、
目標との差に比例した力で押し続ける。つまむ動作で「目標を物体の内側に設定して、力で挟む」のはこの性質を使っている。

このプロジェクトの値: 指 `kp=40, kv=1.5`、手のひら(重いので強く) `kp=2000, kv=100`。

### 1.6 接触と摩擦
物体をつかめるかは、ほぼ**接触と摩擦の設定**で決まる。

- `friction="1.5 0.02 0.002"`: 3つの値は「滑り摩擦, ねじり摩擦, 転がり摩擦」の係数。
  1.5 は大きめ(ゴムのように滑りにくい)。値が小さいと物体が滑り落ちる。
- `condim="4"`: 接触で考慮する成分の数。4 は「滑り(2方向) + 法線 + ねじり」まで考える設定で、把持向き。
- `cone="elliptic"` と `impratio="10"`: 摩擦円錐の計算方法。把持では、滑りにくく正確になる設定を使う。

**シミュレーションの摩擦は現実と一致しない**。これが sim と実機の差 (sim2real ギャップ) の主な原因の1つ。

## 第2部 コードを組み立てるときのポイント

### ポイント1: シミュレータの操作を 1 か所に閉じ込める
`HandEnv` クラスは MuJoCo の細かい関数 (`mj_step` など) を包み、`reset / step / render` のような短い名前だけを外に見せる。

```
  制御のコード ──→ HandEnv ──→ MuJoCo
  (grasp.py)     (env.py)
```

**なぜか**: 将来、実機を動かすときは `HandEnv` と同じ口 (`step`, `joint_pos` ...) を持つ「実機版」を作り、差し替える。
制御のコードは変えずに済む。この考え方を「**抽象化**」または「**インタフェースの分離**」と呼ぶ。

### ポイント2: 「動作の定義」と「実行」を分ける
`grasp.py` は「どう動かすか(時刻→指令値)」だけを持ち、シミュレーションを回す役目はスクリプト側が持つ。

- `ctrl_at(t)` は「時刻 t を渡すと指令値が返る」だけの関数。MuJoCo を知らない。
- そのおかげで、動画を作るスクリプト (`demo_grasp.py`) と GUI (`view_grasp.py`) が**同じ動作**を使える。
- 動作を変えるとき、1 か所を直せば両方に反映される (重複しない)。

### ポイント3: 結果を「数値で判定」できるようにする
目で動画を見て「成功っぽい」ではなく、`z > SUCCESS_Z` のように**プログラムが成否を決める**。

- 自動テスト、パラメータの掃引、回帰確認ができる。
- 終了コード (`sys.exit(0 or 1)`) で成否を他のプログラムに伝えられる。
- ただし**判定基準が緩いと、間違った成功を見逃す** (第5部の実例)。

### ポイント4: 再現性を確保する
- 初期状態に戻せる (`reset`)。
- 乱数を使うなら種 (seed) を固定する。 (今回は乱数なし)
- 値は定数にまとめて名前をつける (`SUCCESS_Z`, `PHASES`)。コードの途中に数字を直書きしない。

### ポイント5: 単位と並び順をコメントや定数で明示する
配列は「何番目が何か」が暗黙になりやすく、バグの温床。`grasp.py` の冒頭コメントのように、
並び順 `[手のひら, 左基節, ...]` を必ず残す。単位 (m, rad) も書く。

### ポイント6: 小さく作って、毎回動かして確かめる
今回の進め方がそれ: ①インストール確認 → ②最小のシーン → ③描画 → ④把持 → ⑤GUI。
一度に大きく作らず、段階ごとに動作を確認すると、問題の切り分けが楽になる。

## 第3部 `src/hand_sim/env.py` の解説

### 3.1 全体の役割
`HandEnv` = 「シミュレータを扱う窓口」。持っているものと、できることは次のとおり。

| 持っているもの (属性) | 意味 |
|---|---|
| `self.model` | 変わらない設定 (`MjModel`) |
| `self.data` | 変わる状態 (`MjData`) |
| `self.dt` | 1ステップの時間 [秒] = 0.002 |
| `self._renderer` | カメラ画像を作る道具 (`mujoco.Renderer`)。必要になったとき作る |

| できること (メソッド) | 内容 |
|---|---|
| `reset()` | 初期状態に戻す |
| `step(ctrl, n_substeps)` | 指令を与えて時間を進める |
| `joint_pos()` | 各関節の現在位置を返す |
| `body_pos(name)` | 名前で物体の位置を返す |
| `render(camera, ...)` | カメラ画像を返す |
| `close()` | 後片付け |
| `nu` (プロパティ) | モータの数 |

#### `_renderer` と `render` は別物? どちらもカメラ関連?
**どちらも「カメラ画像を作る」ためのもので、同じ仕事の「道具」と「操作」の関係。** 種類が違う。

| | `self._renderer` | `render(...)` |
|---|---|---|
| 種類 | **属性** (変数。`self.xxx` に入れた値) | **メソッド** (`HandEnv` の関数) |
| 中身 | `mujoco.Renderer` という **MuJoCo 製の部品 (オブジェクト)** | 「カメラ画像を返す」という **処理の手順** |
| たとえ | **カメラ本体** | **シャッターを押して写真を受け取る操作** |
| 誰が使う | `HandEnv` の内部だけ (`_` 付き = 外から触らない) | 外のコード (`demo_grasp.py` など) が呼ぶ |

- `render()` の中で `self._renderer` を使って画像を作っている。つまり「`render` が `_renderer` を使う」。
- **`_renderer` は「シミュレーション自体の描画」ではなく、カメラ画像を作る専用の道具。** 物理計算 (`mj_step`) とは無関係で、
  `data` を**読むだけ**で書き換えない。だから描画しなくてもシミュレーションは動く (数値だけの検証では `_renderer` は `None` のまま)。
- 「どのカメラか」は `render(camera="front")` の引数で決まる。`"front"`, `"top"` は `scene.xml` の `<camera name=...>` で定義した名前。
  カメラの位置・向きは `model` (変わらない設定) の一部。
- `_renderer` がずっと `None` で、`render()` を初めて呼んだときに作られる理由は、3.3 と 3.7 を参照。

### 3.2 `DEFAULT_MODEL` (モデルファイルの場所)
```python
DEFAULT_MODEL = Path(__file__).resolve().parents[2] / "models" / "scene.xml"
```
- `__file__` は「このファイル自身の場所」。
- `.resolve()` で絶対パスにする。
- `.parents[2]` は親フォルダを 2 つさかのぼる。`src/hand_sim/env.py` → `hand_sim` → `src` → **プロジェクト直下** に着く (`[0]`=hand_sim, `[1]`=src, `[2]`=直下)。
- `/ "models" / "scene.xml"` で、パスをつなぐ。

**なぜこう書くか**: 「どこから実行しても」モデルが見つかるように、このファイルの位置を基準にして探す。
"models/scene.xml" と相対パスで書くと、実行する場所によって見つからなくなる。

### 3.3 `__init__` (準備)
```python
self.model = mujoco.MjModel.from_xml_path(str(model_path))
self.data = mujoco.MjData(self.model)
self.dt = self.model.opt.timestep
self._renderer = None
```
- XML を読み込んで `model` を作り、そこから `data` を作る。第1部の 1.2 のとおり。
- `str()` は、Path を文字列に直している (MuJoCo は文字列を要求する)。
- `_renderer` の先頭 `_` は「内部用なので、外から触らないで」という慣習。
- 最初は `None` (空) にし、**描画するときに初めて作る**。画面が要らない用途 (数値だけの検証) では、描画部品を作らずに済む。

### 3.4 `reset` (初期化)
```python
mujoco.mj_resetData(self.model, self.data)   # data を初期状態に
mujoco.mj_forward(self.model, self.data)     # 時間は進めず、派生値を計算
```
`mj_resetData` だけだと、位置 (`qpos`) は初期値に戻っても、そこから**計算で求める値 (派生値)** が計算されていない状態になる。
`mj_forward` で一度計算し直すことで、**リセット直後でも正しい値が読める**。

#### 「派生値」とは? (実測した例)
`data` には 2 種類の値が入っている。

- **元になる値**: `qpos` (関節の位置) など。シミュレーションの「原因」。`mj_resetData` が初期値に戻す。
- **そこから計算して求める値 (= 派生値)**: 各 body の世界座標での位置 `xpos`、接触 (どこがぶつかっているか)、関節にかかる力など。
  例えば「指先の世界座標」は、手のひらの高さと各関節の角度を順にたどって**計算しないと分からない**。

`mj_resetData` は `qpos` を戻し、派生値は **ゼロ (未計算) の状態にする**だけで、計算し直してはくれない。
このプロジェクトのモデルで、シミュレーションを少し動かしてから試すと次のとおりだった。

| タイミング | `target` の `xpos` | `palm` の `xpos` |
|---|---|---|
| `mj_step` を 500 回実行した後 | `[0, 0, 0.0199]` | (動いた後の値) |
| `mj_resetData` の直後 | `[0, 0, 0]` ← **間違い** (本当は 0.02) | `[0, 0, 0]` ← **間違い** (本当は 0.22) |
| そのあと `mj_forward` を呼ぶ | `[0, 0, 0.02]` ← 正しい | `[0, 0, 0.22]` ← 正しい |

つまり、`mj_forward` を省いて `reset()` 直後に `body_pos("target")` を呼ぶと、**エラーにならず、全部 `[0, 0, 0]` という嘘の値が返る**。
`mj_forward` は「時間は進めずに、今の `qpos` などから派生値だけを計算する」関数。
(`mj_step` を 1 回呼べば同じく計算されるが、その場合は時間が 1 ステップ進んでしまう。「時間を進めずに」が `reset` では大事。)

### 3.5 `step` (時間を進める。最重要)
```python
self.data.ctrl[:] = ctrl           # ①指令を書き込む
for _ in range(n_substeps):        # ②その回数だけ
    mujoco.mj_step(self.model, self.data)   # ③1ステップ進める
```
- ① `ctrl` は長さ 5 の配列。`[:] =` は「中身を丸ごと上書き」。

#### ①では「どのモータか」を指定していないのか? 複数のモータがある場合は?
**指定していないのではなく、「配列の何番目か」で指定している。** 5 個のモータへの指令を**まとめて 1 回で**書き込んでいる。

`scene.xml` の `<actuator>` に書いた順番が、そのまま `ctrl` の添字になる (第1部 1.4 の `qpos` と同じ考え方)。

```
<actuator> に書いた順    ctrl の添字    動かす関節     CLOSE のときの値
 a_palm_z                ctrl[0]       palm_z        -0.115  (手のひらを 11.5cm 下げた位置)
 a_l_prox                ctrl[1]       l_prox        -0.3    (左指の付け根の目標角度 [rad])
 a_l_dist                ctrl[2]       l_dist        -0.2
 a_r_prox                ctrl[3]       r_prox         0.3
 a_r_dist                ctrl[4]       r_dist         0.2
```

- 各モータがどの関節を動かすかは、XML の `<position name="a_l_prox" joint="l_prox"/>` の **`joint="..."`** で決まっている。
  Python 側はそれを意識せず、「`ctrl` の i 番目 = i 番目のモータの目標位置」とだけ考えればよい。
- だから `env.step([-0.115, -0.3, -0.2, 0.3, 0.2])` のように**全モータ分の値を一度に渡す**。
  `grasp.py` の `OPEN` や `CLOSE` が長さ 5 の配列なのは、これに合わせているため。
- **モータが増えたら**: `<actuator>` に行を足せば `ctrl` が長くなる (`nu` も増える)。`env.py` の `step` は変更不要
  (`ctrl[:] = ...` は長さが合っていれば何個でも書き込める。長さが違うとエラーになる)。
  ただし `grasp.py` の姿勢の配列も同じ長さにそろえる必要がある。
- **1 個だけ変えたいとき**は、名前や番号で指定できる。
  ```python
  data.ctrl[1] = -0.3                              # 番号で指定 (添字は <actuator> の順)
  data.ctrl[model.actuator("a_l_prox").id] = -0.3  # 名前から番号を引く (順番が変わっても壊れにくい)
  ```
  このプロジェクトの `step` は「全部まとめて渡す」方式。(全部まとめて渡す書き方は、シンプルで間違いにくいので定番。)
- 「関節の順」ではなく「**アクチュエータの順**」である点に注意。今回はたまたま同じ並びだが、別のモデルでは関節の数とモータの数は一致しないことがある
  (モータが付いていない関節や、関節を複数動かすモータもある)。
- ③ `mj_step` が物理を `dt` 秒進める。関節の力・衝突・摩擦などをまとめて計算する。
- `n_substeps` を大きくすると、**同じ指令のまま複数ステップ進める**。
  (たとえば制御は 50Hz で出すが、物理は 500Hz で回したい、といった場合に使う。)

### 3.6 `joint_pos` と `body_pos` (状態を読む)

(この節は第1部 1.4 の `qpos` の説明が前提。1.4 を先に読み直すこと。)

```python
return self.data.qpos[: self.model.nu].copy()　
return self.data.body(name).xpos.copy()
```

- `qpos[:nu]` は先頭 nu(=5) 個。`[: n]` は「先頭から n 個」を取り出すスライス。
  第1部 1.4 のとおり、`qpos` の先頭 5 個は `[palm_z, l_prox, l_dist, r_prox, r_dist]` の値 (手のひらの高さ [m] と、4 つの指関節の角度 [rad])。
  これは**ハンドの関節が物体より前に書いてある**という前提に頼った書き方で、XML の順序を変えると静かに壊れる。
  (`nu` は「モータの数」だが、ここでは「ハンドの関節の数」の代わりとして使っている。両方 5 で一致しているから成り立つ。)
- `data.body("target")` は名前で body を引く。`.xpos` はその**世界座標での位置** [x, y, z]。
- **`.copy()` が重要**: `data` の中身は毎ステップ**同じ場所で上書き**される。コピーしないと、
  取得した値が次のステップで勝手に変わってしまう。「値のスナップショットを返す」ために必須。

### 3.7 `render` (カメラ画像)
```python
if self._renderer is None or (サイズが変わった):
    self._renderer = mujoco.Renderer(self.model, height=height, width=width)
self._renderer.update_scene(self.data, camera=camera)
return self._renderer.render()
```
- `Renderer` は作るのが重いので、**使い回す**。サイズが変わったときだけ作り直す。
- `update_scene` で「今の状態」を描画部品に反映してから、`render()` で画像にする。

#### 「描画部品」とは?
ここでの「描画部品」は **`self._renderer` (`mujoco.Renderer`)** のこと。
その内部には、**「描画用の現場写真リスト」(MuJoCo の用語では scene)** がある。
中身は「どの形が、どの位置・向きで、何色で、どこにあるか」と、光やカメラの情報。

写真撮影にたとえると次のとおり。

```
data (シミュレーションの本物の状態)    ← 毎ステップ変わる。ここは物理計算の持ち物
   │ ① update_scene(data, camera=...)    今の位置・向きを「撮影用の舞台」に並べ直す (コピー)
   ▼
Renderer 内部の scene (撮影用の舞台)     ← 前回撮った時点の配置のまま止まっている
   │ ② render()                          カメラから見た絵を描き、画素の配列にする
   ▼
画像 (高さ, 幅, 3) の配列
```

- `scene` は **`data` と自動では連動しない**。`mj_step` で物理を進めても、`update_scene` を呼ぶまで舞台は古い配置のまま。
  そのため `render()` の前に毎回 `update_scene` が必要 (忘れると、**ずっと同じ古い画像**が返る)。
- `update_scene` の `camera="front"` で「どのカメラから見るか」も決まる。
- `Renderer` は GPU (描画用のチップ) に画像を描く準備 (メモリの確保など) を伴うので、作るのが重い。
  だから `__init__` では作らず、`render()` を初めて呼んだときに 1 回だけ作って、以降は使い回している (`close()` で片付ける理由もここ)。
- 戻り値は **形 (高さ, 幅, 3) の配列**で、最後の 3 は RGB。**画像処理にそのまま渡せる**。
  次のステップ(カメラ認識)では、この画像を認識に使う。

### 3.8 `close` (後片付け)
描画部品が使った GPU 資源を解放する。呼ばずに終了すると、終了時に EGL のエラー表示が出ることがある
(実際に最初のテストで出た)。「**確保したものは返す**」は、ファイルやウィンドウでも共通の基本。

## 第4部 `src/hand_sim/grasp.py` の解説

### 4.1 全体の役割
「つかむ動作」を**データ**として表現する。コードの中に「手順」を書くのではなく、
**「目標姿勢のリスト」** として並べる。

```
 OPEN ──0.5秒──▶ DOWN ──1.0秒──▶ CLOSE ──1.0秒──▶ LIFT ──1.5秒──▶ (保持)
 開く            手を下げる         指を閉じる         持ち上げる
```

こうすると、動作の追加・変更は**リストを編集するだけ**で済む。
ここでいう**リスト**というのはここでの**つかむ動作**を作成するためにしか使えない。
このリストを使ってつかむ動作（開く...持ち上げて、1.5秒保持）をつくっているのであってこのリストから**つかんで投げる動作**は作成できない

### 4.2 姿勢の定義
```python
OPEN  = np.array([-0.0, -0.1, -0.1,  0.1,  0.1])
DOWN  = OPEN.copy();  DOWN[0]  = -0.115
CLOSE = DOWN.copy();  CLOSE[1:] = [-0.3, -0.2, 0.3, 0.2]
LIFT  = CLOSE.copy(); LIFT[0]  = -0.02
```
- 並び順は `[手のひら, 左基節, 左先節, 右基節, 右先節]`。
- **左右で符号が逆**: 左指は負、右指は正。左右の指が内側に曲がる向きが逆だから。手のひらの中央を0とするローカル軸があるイメージで考えると良い
  (`scene.xml` で、左指の可動範囲を `-1.2〜0.1`、右指を `-0.1〜1.2` としているのと対応。)
- 手のひらの値は「初期位置からのずれ」。`-0.115` は 11.5 cm 下げる (物体の高さまで届く量)。手のひらにはワールド軸が存在する。
- **`.copy()` を使う理由**: `numpy` の配列は代入しても「同じもの」を指すだけ。
  コピーせずに `DOWN = OPEN` として `DOWN[0] = ...` とすると、`OPEN` まで書き換わってしまう。
  「**前の姿勢をベース**に、一部だけ変えた新しい姿勢」を作るときの定番の書き方。
- `[1:]` は「2番目以降」(先頭を除く)。指の4つの値だけを一度に設定している。

### 4.3 `PHASES` と `SUCCESS_Z`
```python
PHASES = [(OPEN, 0.5), (DOWN, 1.0), (CLOSE, 1.0), (LIFT, 1.5)]
SUCCESS_Z = 0.08
```
- `PHASES` は `(目標姿勢, かける時間)` の組のリスト。
- `SUCCESS_Z` は成功の基準(物体の高さ 8cm 以上)。**数字を名前で管理**するので、変更が1か所で済む。ここでは単純に高さを入れていて**何をどうしたらok**という情報はここにはない

### 4.4 `ctrl_at(t)` (時刻 → 指令値)
```python
def ctrl_at(t):
    prev, start = OPEN, 0.0
    for goal, dur in PHASES:
        if t < start + dur:
            return prev + (goal - prev) * (t - start) / dur
        prev, start = goal, start + dur
    return prev
```
動きを順に追うと次のとおり。

1. `prev`=出発姿勢、`start`=今の区間の開始時刻。最初は OPEN から時刻 0 で始まる。
2. 区間を順に見て、**時刻 t がその区間に入っていれば**、補間した値を返して終了。
3. 入っていなければ、次の区間へ進む: 出発姿勢を今の目標に、開始時刻を区間の長さだけ進める。
4. 全区間を過ぎたら、最後の姿勢をそのまま返す (保持)。

**線形補間** の式: `出発 + (目標 − 出発) × 進み具合`。進み具合 = `(t − start) / dur` で 0〜1。

```
  進み具合 0 → 出発姿勢そのもの
  進み具合 0.5 → ちょうど中間
  進み具合 1 → 目標姿勢
```

- 配列同士の引き算・足し算・掛け算は **numpy が要素ごとに一括計算**してくれる (5個の値を同時に補間)。
- この関数は**純粋** (同じ入力なら必ず同じ出力、外部状態に依存しない)。だからテストしやすく、再利用しやすい。
- 使い方: `env.step(ctrl_at(現在の時刻))` を毎ステップ呼ぶ。

### 4.5 この「決め打ち動作」の限界
今の動作は **物体が必ず原点にある前提**。物体の位置が変わると失敗する。
次のステップ(カメラで位置を取る)では、`DOWN` や `CLOSE` の値を**認識した位置から計算して作る**ことになる。
つまり `grasp.py` は、将来「位置を入れると動作を返す関数」に発展する部分。

## 第5部 検証の進め方 (今回の実例)

### 実例: 「成功」と出たが、間違っていた
最初、指を大きく曲げた設定 (基節 0.9, 先節 0.5) で `GRASP SUCCESS` (物体 z=0.171) と出た。
しかし最終フレームの画像を見ると、**指で物体を下から掬い上げ、手のひらに押し付けているだけ**だった。
手のひらは 9.5cm しか上がっていないのに、物体は 15cm 上がっていたのが手がかり。

教訓:
1. **成功判定は「結果が正しい理由」まで見ないと、誤った成功を通す。** (最初の基準 `z > 0.06` は甘かった)
2. **数値だけでなく、画像・動画でも確認する。**
3. **「手のひらに対する物体の相対位置」** のように、**原因を表す指標**を使うと見抜ける。

### パラメータ掃引
基節 (0.3〜0.6) × 先節 (0.0〜0.4) の全組み合わせを自動で実行し、各結果を表にして比較した。
これは CUI で動かす最大の利点。結果:

| 基節 | 先節 | 手のひらに対する物体の相対高さ | 判断 |
|---|---|---|---|
| 0.3 | 0.2 | −0.082 | **挟んで持ち上げ (下降時 −0.085 とほぼ同じ=滑っていない)** |
| 0.6 | 0.2 | −0.028 | 掬い上げ(物体が手のひらへ近づいた) |

「持ち上げている間に相対位置が変わらない」= 滑らずに保持できている、という判断基準。

## 第6部 つまずきやすい点

| 症状 | 原因と対処 |
|---|---|
| `import hand_sim` でエラー | `src` が import の探索先に入っていない → `sys.path.insert(0, ".../src")` が必要 |
| 描画で `EGL` のエラー | `MUJOCO_GL=egl` を **mujoco を import する前**に設定する |
| 終了時に EGL エラーの長い表示 | `env.close()` を呼ぶ |
| 取得した位置が勝手に変わる | `.copy()` を付け忘れている |
| 指が動かない・逆向きに動く | `ctrl` の並び順、左右の符号 (正負) を確認 |
| 物体が滑って落ちる | 摩擦 (`friction`)、指の位置、`kp` (握る力) を調整 |
| シミュレーションが発散・振動 | `kp` が大きすぎる、`kv` が小さすぎる、タイムステップが大きすぎる |
| 動画が作れない | `ffmpeg` が必要 → `imageio-ffmpeg` を使う (導入済み) |
