# 視覚サーボの"目": 2つの手法の概要

`src/hand_sim/vision.py` に書く2つの関数の考え方をまとめる。答え合わせは `scripts/check_vision.py`。

```
カメラ画像 --①色で物体の画素を選び、重心を求める--> 画像上の位置 (u, v) [画素]
           --②ピンホールカメラの式で実寸に直す-->    世界座標の位置 (x, y) [m]
```

---

## 前提: 画像は「数値の配列」

`renderer.render()` が返す画像は、numpy の配列。


| 項目                 | 内容                                                             |
| ------------------ | -------------------------------------------------------------- |
| 形 (`img.shape`)    | `(高さ, 幅, 3)`。今回は `(480, 640, 3)`                               |
| 3 の意味vision_basics | 最後の軸が色の3成分: `[:, :, 0]`=R(赤)、`[:, :, 1]`=G(緑)、`[:, :, 2]`=B(青) |
| 型 (`img.dtype`)    | `uint8`(0〜255 の整数)                                             |
| 画素の指定              | `img[v, u]`。**縦(行)が先、横(列)が後**。                                 |


座標の呼び方は2つあり、混同しやすい。


|       | 横方向                   | 縦方向                   |
| ----- | --------------------- | --------------------- |
| 画像の座標 | **u**(左端が0、右へ増える)     | **v**(上端が0、**下へ**増える) |
| 配列の添字 | 2番目 `img[v, u]` の `u` | 1番目 `img[v, u]` の `v` |


> 落とし穴 (`uint8`): 255 を超える計算は**あふれて 0 に戻る**。`img * 2` で 200 → 144 になる。
> 比較や `0.4 * r` のように小数を掛ける分には、float になるので問題ないが、
> 整数のまま足し算・掛け算をするときは `.astype(float)` で型を変えてから計算する。



### `img` の中身と、`r = img[:, :, 0]` で何が起きるか

`img` は、**全画素の色を全部入れた、入れ物の配列**。2行×3列の画像なら、次の形になる。

```python
img = [
  [ [200, 20, 30],  [50, 200, 40],  [230, 220, 60] ],   # 1行目: 3画素
  [ [210, 25, 15],  [90,  80, 70],  [ 10,  15, 190] ],   # 2行目: 3画素
]
```

`[200, 20, 30]` のような3つの数が、**1画素の (R, G, B)**。
全部で 2×3 = 6 画素あるので、`img` の中には6つの (R, G, B) が入っている(`img.shape` は `(2, 3, 3)`)。

取り出し方:


| 書き方            | 取り出されるもの                   |
| -------------- | -------------------------- |
| `img[0, 0]`    | 1行目・1列目の画素 → `[200 20 30]` |
| `img[0, 0, 0]` | その画素の R だけ → `200`         |
| `img[1, 2]`    | 2行目・3列目の画素 → `[10 15 190]` |


`r = img[:, :, 0]` **の後、**`r` **に入るもの**

画素の色(R, G, B の3つ組)は入らない。**6画素それぞれの R の値だけ**が入る(形は `(2, 3)`)。

```
img (6画素の (R,G,B))                                  r = img[:,:,0]
 [ (200, 20, 30)   (50, 200, 40)   (230, 220, 60) ]    [[200   50  230]
 [ (210, 25, 15)   (90,  80, 70)   ( 10,  15,190) ]     [210   90   10]]
     ↑                                                      ↑
   各画素の1つ目の数(R)だけを、同じ位置に並べる
```

`g` と `b` も同じ要領で、各画素の2つ目の数、3つ目の数だけを集める。

```
g = img[:,:,1]             b = img[:,:,2]
[[ 20  200  220]           [[ 30   40   60]
 [ 25   80   15]]           [ 15   70  190]]
```

3つの配列は**同じ位置が同じ画素に対応**する。左上の画素 `(200, 20, 30)` は、
`r[0,0]=200`、`g[0,0]=20`、`b[0,0]=30` にバラして入っている。
バラしておくと、`g < 0.4*r` のような「同じ画素の G と R の比較」を、
**同じ位置どうしの比較として一行で**書ける(後の「マスクを作る」で使う)。

自分の環境で確かめるには:

```python
print(img.shape)        # (2, 3, 3)
print(img[0, 0])        # 1つの画素: [200 20 30]
print(r)                # R だけの 2×3 配列
```

## ① 色で物体の画素を選び、重心を求める (`find_red_centroid`)



### 考え方

1. **マスク**を作る: 画素ごとに「赤いか?」を判定し、True/False の配列にする。
2. True の画素の位置(u, v)を取り出す。
3. その**平均**が重心(物体の中心の目安)。

？？？？マスクを作るというのはimg[v, u]から取得して

> **回答**: 「`img[v, u]` を1画素ずつ取り出して判定する」のではなく、**画像全体を一度に判定する**のが numpy の書き方です。
> マスクは「画像と同じ縦横サイズ(`(480, 640)`)の True/False の配列」で、`mask[v, u]` が True なら「その画素は赤い」を表します。
> 1画素ずつ書く方法(遅い)と、配列ごと書く方法(速い・短い)は、**同じ結果**になります(このシーンで実測: どちらも 930 画素)。
>
> ```python
> # (A) 1画素ずつ(ループ)。意味は分かりやすいが、遅く、長い。
> for v in range(480):
>     for u in range(640):
>         r, g, b = img[v, u]                  # この画素の色
>         if r > 100 and g < 0.4*r and b < 0.4*r:
>             ...                              # 赤い画素だった
>
> # (B) 配列ごと(numpy)。ループを書かない。
> r = img[:, :, 0]   # 「全画素の R」だけを取り出した (480, 640) の配列
> g = img[:, :, 1]
> b = img[:, :, 2]
> mask = (r > 100) & (g < 0.4*r) & (b < 0.4*r)   # (480, 640) の True/False
> ```

＊img = [横のピクセル数, 縦のピクセル数, ３種類の色わけ（0, 1, 2）]

> `img[:, :, 0]` の `:` は「その軸を全部」の意味で、「全ての v、全ての u の、R 成分」となります。
> (B) の `r > 100` は、全画素に対する比較が1行で行われ、結果は True/False の配列になります。



### 「赤い」の判定

赤 = R が大きく、G と B が R に比べて十分小さい。例: `R > 100` かつ `G < 0.4*R` かつ `B < 0.4*R`。
アームの黄色は R も G も大きいので、`G < 0.4*R` で除外される。　
？？？？この条件は一般的な基準ですか？それとも都度自分で考えなければならないもの？

> **回答**: **数値(100 や 0.4)は決まった基準ではなく、場面ごとに決めるもの**です。私が例として置いた値です。
> 「R が大きく G・B が小さい」という**考え方**は一般的ですが、具体的な境目は、カメラ・照明・物体の色で変わります。
>
> 決め方の手順(定番):
>
> 1. 実際の画像で、物体の画素の色を `print(img[v, u])` で見る。
> 2. 背景や他の物(アームの黄色、白い床)の色も見る。
> 3. 物体の色は含み、他は含まない境目を、余裕を持って決める。
>
> このシーンで実測した値:
>
>
> | 対象           | 色 (R, G, B)                                        |
> | ------------ | -------------------------------------------------- |
> | 赤い立方体の明るい面   | (255, 68, 68)                                      |
> | 赤い立方体の影になった面 | R が 115 まで下がる。G, B は最大 70                          |
> | 床の背景         | (255, 255, 255)(白く飛んでいる)                           |
> | アームの黄色       | R, G ともに大きい。G/R は 0.81〜1.0(例: 影の部分で (108, 87, 13)) |
>
>
> 影の面でも R が 115 なので、「R > 100」にして拾っています。`G < 0.4*R` は、赤(実測で G/R は最大 0.27)は通し、黄色(G/R は 0.81 以上)は通さない、2つの間の値として選びました。
> 色の割合で判定している理由は、明るさが変わっても「R に対する G・B の割合」は比較的変わらないからです(完全ではありません)。
>
> **実機の場合**: 照明が変わると色の値が変わるので、境目の調整が必要になります。
> 画像処理では、明るさと色味を分けて扱える **HSV** という色表現に直してから条件を書くのが一般的です(OpenCV の `cv2.cvtColor`)。
> 今回は追加ライブラリなしの RGB で足りています。実機で崩れたら、HSV への切り替えも検討します。



### numpy の道具


| 書き方                                         | 意味                                                |
| ------------------------------------------- | ------------------------------------------------- |
| `r > 100`                                   | 配列の**全要素**を同時に比較して、True/False の配列を返す(ループ不要)       |
| `(A) & (B)`                                 | 要素ごとの「かつ」。**各条件を** `()` **で囲む**(`and` は配列には使えない)  |
| `mask.any()`                                | 1つでも True があるか                                    |
| `mask.sum()`                                | True の個数                                          |
| `np.nonzero(mask)`                          | True の位置を `(行の配列, 列の配列)` の順で返す = `(v の配列, u の配列)` |
| `配列.mean()`                                 | 平均                                                |
| ？？？？全体的にイメージできないもう少し詳しく書いて。特に`(A) & (B)`の部分 |                                                   |


> **回答**: 画素4個だけの、1列の配列で動かしてみます(画像の「ある1行」だと思ってください)。
>
> ```python
> r = np.array([200,  50, 220,  30])   # 4画素の R
> g = np.array([ 20, 200,  30,  25])   # 4画素の G
> ```
>
> **①** `r > 100` **: 全要素を一度に比較する。結果は True/False の配列。**
>
> ```
> r         = [200,   50,  220,   30]
> r > 100   = [True, False, True, False]    ← 1画素目と3画素目だけ R が 100 より大きい
> ```
>
> **②** `g < 50` **: 同じく別の条件の配列。**
>
> ```
> g         = [ 20,   200,   30,    25]
> g < 50    = [True, False, True,  True]
> ```
>
> **③** `A & B` **: 同じ位置の2つを見て、「両方とも True のときだけ True」。**(要素ごとの「かつ」)
>
> ```
> A       = [True, False, True,  False]
> B       = [True, False, True,  True ]
> A & B   = [True, False, True,  False]     ← 1つ目と3つ目だけ、両方の条件を満たす
> ```
>
> 1つ目と3つ目の画素は「R が大きく G が小さい」= 赤っぽい画素、ということです。
> 3つ以上の条件でも `(A) & (B) & (C)` のように、「全部 True の画素だけ」が True になります。
>
>
> | 記号  | 意味          | 例           |
> | --- | ----------- | ----------- |
> | `&` | 要素ごとの「かつ」   | `(A) & (B)` |
> | `|` | 要素ごとの「または」  | `(A) | (B)` |
> | `~` | 要素ごとの「ではない」 | `~A`        |
>
>
> **よくある間違い2つ(どちらも実際にエラーになります)**
>
> - `A and B` と書く: `ValueError: The truth value of an array with more than one element is ambiguous`。
> Python の `and` は「配列全体で1つの True/False」を求めるので、配列には使えません。配列には `&` を使います。
> - `()` を付けない `r > 100 & g < 50`: 同じエラー。`&` は `>` や `<` より先に計算されるので、`100 & g` が先に計算されてしまいます。
> **各条件を** `()` **で囲む**のは、この計算順序を直すためです。
>
> 画像でも同じことを、`(480, 640)` の配列で行っているだけです。



### 小さな例 (4行×5列の画像)

赤い画素が `(v,u) = (1,2)`, `(1,3)`, `(2,3)` の3つ、黄色が1つある画像で:

```python
mask = (r > 100) & (g < 0.4 * r) & (b < 0.4 * r)
```

```
mask (1=赤い):          vs, us = np.nonzero(mask)
 u→ 0 1 2 3 4              vs = [1 1 2]   ← 行(縦)の位置
v0   0 0 0 0 0             us = [2 3 3]   ← 列(横)の位置
v1   0 0 1 1 0             us.mean() = 2.67,  vs.mean() = 1.33
v2   0 0 0 1 0             → 重心 (u, v) = (2.67, 1.33)
v3   0 0 0 0 0
```

黄色の画素 `(3, 0)` はマスクに入っていない(G が大きいため)。

### 注意点

- 戻り値は `(u, v)` の順。`np.nonzero` の戻りは `(v, u)` の順なので**逆になる**。？？？？(u, v)はなにの戻り値？

> **回答**: これは、**あなたが書く** `find_red_centroid` **関数の戻り値**(`return` で返す値)です。
> 戻りの形は、骨組みの docstring と `check_vision.py` で `(u, v)` の順と決めてあります(`uv[0]` が u、`uv[1]` が v として使われます)。
>
> 一方、`np.nonzero(mask)` は numpy 側が返す値で、順番は `(vs, us)`(行=縦が先)です。
> 配列は「縦が先、横が後」(`img[v, u]`)なので、numpy はそれに合わせています。
>
> ```python
> vs, us = np.nonzero(mask)       # numpy が返す順: 縦(v)が先
> ...
> return u_center, v_center       # あなたの関数が返す順: 横(u)が先 ← 順番を入れ替えて返す
> ```
>
> つまり、受け取るときの順番と、返すときの順番が、逆になるので注意、という意味です。

- 赤い画素が1つも無いと、空の配列の平均は `nan`(エラーにはならず、警告だけ出る)。
先に `mask.any()` で確認し、無ければ `None` を返す。
- 条件の数値(100 や 0.4)に決まりはない。実機では照明で変わるので、調整が必要になる。

## ② 画素の位置を実寸に直す (`pixel_to_world`)



### 考え方: ピンホールカメラ

カメラは「小さな穴から入った光が、奥の板(画像)に映る」モデルで表せる。
物体が**カメラから遠いほど、同じ実寸でも画像上では小さく**写る。
今回は真下を向いたカメラで、物体の面の高さが分かっているので、
**画素1つが何 m に当たるか**を決められる。

```
        カメラ(高さ cam_z)
          │ ＼
 焦点距離 f │   ＼        f [画素] : depth [m] = 画像上のずれ [画素] : 実際のずれ [m]
          │     ＼
   画像 ──┴────────      (相似な三角形)
          │         ＼
 depth    │           ＼
          │             ＼
   物体の面(高さ z_obj) ─────●─
```

相似な三角形から:

```
実際のずれ [m] = (画像上のずれ [画素]) ÷ f × depth
```



### 3つの量


| 量                                                     | 式                            | 意味                                                                             |
| ----------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------ |
| 焦点距離 `f` [画素]                                         | `(height/2) / tan(fovy/2)`   | 画像の縦の半分が、視野角の半分に当たる、という関係から決まる。`fovy` は**度**で渡されるので、`np.radians` で**ラジアンに直す**。 |
| 奥行き `depth` [m]                                       | `cam_pos[2] - z_obj`         | カメラから、見ている面までの距離。**物体の上面**の高さ(立方体なら 0.03 m)を使う。                                |
| 画像上のずれ [画素]                                           | `u - width/2`、`v - height/2` | 画像の中心(カメラの真下に当たる点)からのずれ。                                                       |
| u、vはピクセルの座標を意味していて、中心位置（width/2, height/2）からの距離を出している |                              |                                                                                |


> ```
> 画像(横 640 画素、縦 480 画素)
>
>  u=0                    u=320 (= width/2)               u=640
>   ┌────────────────────────┼────────────────────────┐ v=0
>   │                        │                        │
>   │                        │                        │
>   ├────────────────────────●────────────────────────┤ v=240 (= height/2)
>   │                        │       ● 赤い物体 (u=420, v=300)
>   │                        │                        │
>   └────────────────────────┴────────────────────────┘ v=480
> ```
>
> - `u` は「物体が左から何画素目か」(例: 420)。
> - `u - width/2` は「画像の中心から、右へ何画素ずれているか」(例: 420 - 320 = **100 画素**)。
> - `v - height/2` も同様に、中心から下へ何画素ずれているか(例: 300 - 240 = **60 画素**)。
>
> どれも画素の数なので、引き算の結果も画素です。これを `/ f × depth` で、**m に変換する**のが次の手順です。
>
> 中心を基準にする理由: カメラが真下を向いているので、画像の中心は「カメラの真下」の点に当たります。
> 「中心からのずれ」が分かれば、「カメラの真下の位置(`cam_pos` の x, y)+ ずれ」で、物体の世界座標が求まるためです。



### 手順

1. `f` を求める。
2. `depth` を求める。
3. 中心からのずれ `(u - width/2, v - height/2)` を、`÷ f × depth` で実寸にする。
4. カメラの真下の位置 `(cam_pos[0], cam_pos[1])` に足して、世界座標にする。

？？？？これはどういう意味？「4. カメラの真下の位置 `(cam_pos[0], cam_pos[1])` に足して、世界座標にする。」あとcam_posには何が入る？

### 符号に注意

`scene_vs.xml` のカメラは「画像の右 = 世界の +x、画像の上 = 世界の +y」。

- **u は右へ増える**: 世界の x も増える → そのまま**足す**。
- **v は下へ増える**: 世界の y は上へ増える → **逆向き**なので**引く**。



### 数値の例 (このシーンのカメラ)

`fovy=45°`、画像 640×480、カメラの高さ 0.6 m、立方体の上面 0.03 m の場合:

- `f = 240 / tan(22.5°) ≈ 579.4` 画素
- `depth = 0.6 - 0.03 = 0.57` m
- 画像の中心から**右に100画素**ずれた点は、`100 / 579.4 × 0.57 ≈ 0.0984` m = 約 9.8 cm だけ +x 側。



### 精度について

赤い画素の重心には、立方体の側面(斜めに見える面)も少し混ざる。そのため、
上面の高さを使っても少しずれるが、この条件では誤差は数 mm 以下(`check_vision.py` の許容は 5 mm)。
これが実機でどれだけ変わるかは、第4週のギャップ計測の材料になる。
